# China Deployment

This deploy target runs the same TanStack Start app on a Mainland China ECS instance.

- Global production: `NITRO_PRESET=cloudflare-module` -> Cloudflare Workers.
- Mainland production: `NITRO_PRESET=node-server` -> Node.js 22 on Volcengine ECS.

## Required Server Inputs

Give the operator these values before the first deploy:

- ECS public IPv4 address, region, operating system, CPU architecture, and SSH port.
- SSH username plus either a private key or a temporary password. The user must have `sudo`.
- Domain names to bind. For the iOS API, use `api.nekoid.cn`; add `www.nekoid.cn` or `nekoid.cn` only after those hosts also point to the ECS instance.
- DNS control for those domains, or exact DNS records that the domain owner will add.
- Security group inbound rules for TCP `22`, `80`, and `443`. Restrict `22` to the operator IP when possible.
- A production env file based on `deploy/china/env.example`.
- Volcengine TOS bucket name, region, endpoint, and an AccessKey pair. iOS media uploads
  and downloads use short-lived TOS signed URLs generated by the Node server, so keep
  the bucket private and keep the AccessKey values server-only.
- TLS choice: Certbot/Let's Encrypt on the server, or a Volcengine certificate and private key.

For the current iOS build, the production API base URL is `https://api.nekoid.cn`.
Make sure DNS points this host to the Volcengine ECS public IP before shipping a
TestFlight or App Store build for Mainland China.

## Build Locally

```sh
npm run build:china
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

Health check:

```sh
curl -i http://127.0.0.1:3000/api/ios/health
```

## Docker Build

The browser bundle needs public Supabase values at build time:

```sh
docker build \
  -f Dockerfile.china \
  --build-arg VITE_SUPABASE_URL=https://your-project-ref.supabase.co \
  --build-arg VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your-public-key \
  -t nekoid-china:latest .
```

Run it:

```sh
docker run --rm \
  --env-file deploy/china/nekoid.env \
  -p 3000:3000 \
  nekoid-china:latest
```

## Bare Node + systemd

Install Node.js 22 on the ECS instance, then place the checked-out repo at:

```text
/opt/nekoid/current
```

Create the env file:

```sh
sudo install -d -m 0750 -o root -g root /etc/nekoid
sudo install -m 0640 deploy/china/env.example /etc/nekoid/nekoid.env
sudo editor /etc/nekoid/nekoid.env
```

Install the service:

```sh
sudo useradd --system --home /opt/nekoid --shell /usr/sbin/nologin nekoid || true
sudo cp deploy/china/nekoid.service /etc/systemd/system/nekoid.service
sudo systemctl daemon-reload
npm ci
npm run build:china
sudo systemctl enable --now nekoid
sudo systemctl status nekoid
```

Install the Nginx reverse proxy:

```sh
sudo cp deploy/china/nginx.conf /etc/nginx/conf.d/nekoid.conf
sudo nginx -t
sudo systemctl reload nginx
```

After DNS resolves to the ECS public IP, enable HTTPS with your chosen certificate flow.

## SSH Deploy

Create a local env file first. This file is ignored by git:

```sh
cp deploy/china/env.example deploy/china/nekoid.env
```

Fill `deploy/china/nekoid.env` with real production values, then run:

```sh
NEKOID_SSH_TARGET=root@1.2.3.4 \
NEKOID_SSH_KEY=/absolute/path/to/key.pem \
NEKOID_DOMAINS="api.nekoid.cn" \
deploy/china/deploy-over-ssh.sh
```

The script uploads the current source, builds `NITRO_PRESET=node-server` on the
server with Node.js 22, installs `/etc/systemd/system/nekoid.service`, preserves
an existing `/etc/nginx/conf.d/nekoid.conf` by default, and checks
`http://127.0.0.1:3000/api/ios/health`.

Set `NEKOID_FORCE_NGINX=1` only when you intentionally want to overwrite the
server Nginx config from `deploy/china/nginx.conf`.

To enable HTTPS with an existing Certbot install after DNS is live:

```sh
NEKOID_ENABLE_CERTBOT=1 \
NEKOID_CERTBOT_EMAIL=ops@example.com \
NEKOID_SSH_TARGET=root@1.2.3.4 \
deploy/china/deploy-over-ssh.sh
```

`NEKOID_CERTBOT_EMAIL` is recommended for certificate-expiry notices, but the
script can still request a certificate without it.

## Verify

### Dedicated App Review phone login

The existing iOS phone/OTP endpoints support **one opt-in review account**. Normal
phone numbers keep using Supabase SMS OTP. No iOS rebuild is needed for this feature.
The fixed review code is checked only on the server; it is not the Supabase password.
A separate random password exchanges for a normal Supabase session, preserving RLS,
refresh tokens, real AI requests and account deletion. The runtime requires the exact
phone, pinned UUID, `authenticated` role and server-owned `app_metadata.neko_app_review`.
It never creates users or uses the admin key to log a user in.

Keep all six `NEKO_REVIEW_LOGIN_*` variables out of git and client bundles. The default
is disabled. `NEKO_REVIEW_LOGIN_EXPIRES_AT` is required; after that deadline the number
returns to normal SMS login. Do not use an account with private personal data: anyone
knowing the review phone and fixed code can access that account. Use a random review
code where possible and disable it when review no longer needs access.

To provision, load the server's Supabase credentials plus the exact review phone,
six-digit code and review expiry from protected environment files (not CLI arguments).
From a release with dependencies installed, first run the dry-run:

```sh
node --env-file=/etc/nekoid/nekoid.env --env-file=/path/to/review-input.env \
  scripts/configure-review-login.mjs
```

The dry-run prints only the target UUID, whether it exists, and expiry. If this is an
existing account, confirm it is the intended test account. Applying changes rotates
only this account's password and adds its review marker; it does not clear its data.
Pass that exact UUID with `--existing-user-id=<UUID>` (omit for a new account):

```sh
node --env-file=/etc/nekoid/nekoid.env --env-file=/path/to/review-input.env \
  scripts/configure-review-login.mjs --apply --existing-user-id=<UUID> \
  --output=/etc/nekoid/review-login.env
```

Output is a new mode-0600 file and still has `NEKO_REVIEW_LOGIN_ENABLED=false`. Test
with the new backend, then merge these six fields into the existing service environment
and set `NEKO_REVIEW_LOGIN_ENABLED=true` during the scoped domestic deployment. Never
replace the whole production env file or upload a local `.env.local`. Do not print the
password, code, access tokens or refresh tokens to logs. Verify login, refresh and an
authenticated read against the real Supabase instance before inviting reviewers.

The current single-process China backend permits one send per 60 seconds and blocks
this review account after five failed/malformed attempts within 15 minutes. Requests
cannot reset this counter by asking for another code; concurrent verification is
serialized. The limiter is **process-local** and resets on restart: before deploying
multiple instances/Workers, replace it with a shared durable limiter. Supabase's normal
password-grant limits also remain in place. Disabling the feature stops new fixed-code
logins but does not revoke already issued sessions; explicitly revoke those if needed.
Deleting the account is real and invalidates the pinned UUID; re-provision deliberately
instead of auto-recreating it during login.

Run `node --test scripts/test-ios-auth.mjs` for isolation and regression checks.

### Account deletion

The native app uses `POST /api/ios/cloud/account/delete` with a user bearer token
and `{ "confirmation": "DELETE" }`. Configure `SUPABASE_SERVICE_ROLE_KEY` with the
**current** project's service_role key in `/etc/nekoid/nekoid.env` (or use
`SUPABASE_SECRET_KEY` for a supported Supabase secret key). Never put it in `VITE_*`,
the iOS project, or source control. Missing admin configuration fails before any
data is deleted. Cloudflare deployments use the same server-only secret names.

The TOS identity also needs ListObjectVersions and DeleteObject/versions permissions
on the media bucket. Cleanup is restricted to the authenticated UUID's prefix,
including abandoned uploads and old versions. Legacy `neko-media` Supabase Storage
objects are cleaned too; an absent bucket is allowed, permission errors are not.
Business rows are deleted with explicit owner filters before Auth hard deletion.
The migration's cascading foreign keys remain an additional safeguard.

A server-owned `app_metadata.neko_account_deletion_pending` flag blocks new API
writes once cleanup starts. Failures retain this flag and login identity so the
user can retry from Settings; only a completed Auth deletion returns success.
Do not clear this flag to claim a partial deletion completed. Existing direct-TOS
upload URLs cannot be revoked individually and remain valid until their short TTL:
before public rollout, arrange a delayed prefix sweep after the upload TTL for
accounts deleted while another device was uploading. Backups follow the separate
backup retention policy; exports already saved to the user's Photos are untouched.

Run `node --test scripts/test-account-deletion.mjs` for isolated failure/ownership
tests. Before enabling in production, verify with **new disposable test accounts**:
create data and media, delete account A, query all four business tables and Auth to
confirm removal, verify A's old access/refresh tokens fail, and confirm account B
and its objects remain. Never test deletion against an existing user's account.

```sh
curl -i http://127.0.0.1:3000/api/ios/health

```
